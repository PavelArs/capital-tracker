## 1. Цель продукта

Сервис предназначен для централизованного учета личного капитала пользователя.

Система должна позволять:

* видеть текущую стоимость всех активов в одном месте;
* отслеживать изменение капитала во времени;
* автоматически получать данные о криптовалютных активах и операциях;
* минимизировать необходимость ручного внесения операций;
* хранить собственную историю стоимости активов независимо от доступности исторических данных внешних API;
* позволять вручную корректировать данные, если автоматическое определение невозможно или ошибочно.

На первом этапе система рассчитана на одного владельца аккаунта.

## 2. Авторизация и безопасность

### 2.1 Авторизация

Пользователь должен иметь возможность войти в систему с помощью:

* email;
* password;
* TOTP-based 2FA.

Самостоятельная регистрация пользователей отсутствует.

Аккаунт владельца создаётся при первоначальном развертывании системы либо административным способом.

### 2.2 Восстановление пароля

Пользователь должен иметь возможность восстановить пароль через email.

Процесс восстановления:

1. пользователь вводит email;
2. система отправляет одноразовую ссылку;
3. ссылка имеет ограниченный срок действия;
4. после использования ссылка становится недействительной;
5. пользователь устанавливает новый пароль.

При восстановлении пароля существующие пользовательские сессии должны быть аннулированы.

### 2.3 Двухфакторная аутентификация

2FA должна быть включена по умолчанию.

Поддерживаемый метод для MVP:

* TOTP (Google Authenticator, 1Password, Bitwarden и аналоги).

Должны поддерживаться recovery codes для восстановления доступа при потере второго фактора.

## 3. Dashboard

Главная страница должна предоставлять агрегированное представление личного капитала.

### 3.1 Общая стоимость капитала

Пользователь должен видеть:

* текущую стоимость всех активов;
* изменение стоимости за выбранный период;
* абсолютное изменение;
* процентное изменение.

Основная валюта отображения должна настраиваться.

Для MVP:

* USD;
* EUR;
* RUB.

### 3.2 История капитала

Система должна отображать график стоимости капитала.

Минимальные периоды:

* 24 часа;
* 7 дней;
* 1 месяц;
* 3 месяца;
* 1 год;
* всё время.

График должен строиться на основании исторических данных, сохранённых системой.

### 3.3 Структура капитала

Пользователь должен видеть распределение капитала:

* по типу активов;
* по валютам/криптовалютам;
* по кошелькам/счетам.

Например:

* BTC — 30%;
* ETH — 20%;
* SOL — 5%;
* Cash — 25%;
* Other — 20%.

## 4. Активы

Система должна поддерживать различные типы активов.

Для MVP:

* cryptocurrency;
* fiat/cash;
* manually tracked asset.

В дальнейшем архитектура должна позволять добавление:

* stocks;
* bonds;
* ETFs;
* bank accounts;
* deposits;
* real estate;
* precious metals;
* liabilities.

Для каждого актива должны храниться как минимум:

* тип;
* название;
* ticker;
* количество;
* текущая стоимость;
* валюта оценки;
* источник данных.

## 5. Рыночные котировки

Система должна автоматически получать котировки активов из внешних источников.

### 5.1 Частота обновления

Котировки должны обновляться минимум один раз в час.

### 5.2 Источники

Используются бесплатные API публичных и проверяемых источников.

Для каждого типа данных должен быть определён основной источник.

Желательно предусмотреть возможность смены поставщика без изменения бизнес-логики приложения.

### 5.3 Исторические данные

После получения котировки система должна сохранять её в собственной БД.

Исторические данные не должны зависеть от дальнейшей доступности внешнего API.

Для записи должны храниться:

* asset;
* price;
* quote currency;
* timestamp;
* data source.

## 6. Криптовалютные кошельки

Пользователь должен иметь возможность добавить публичный адрес криптовалютного кошелька.

Для MVP поддерживаются:

* Bitcoin;
* Ethereum;
* Solana.

Приватные ключи и seed-фразы приложение никогда не запрашивает и не хранит.

Кошельки используются исключительно в read-only режиме.

Для кошелька система должна автоматически получать:

* текущий баланс;
* список транзакций;
* timestamp транзакции;
* asset;
* amount;
* transaction hash;
* network fee;
* sender;
* recipient.

## 7. Операции

Все изменения активов должны представляться через единую сущность Transaction / Operation независимо от источника.

Операции могут быть:

* автоматически импортированными из blockchain;
* созданными пользователем вручную;
* импортированными в будущем из других источников.

### 7.1 Классификация операций

Пользователь должен иметь возможность классифицировать операции.

Основные категории:

* Buy;
* Sell;
* Transfer between own accounts;
* Income;
* Expense;
* Fee;
* Reward;
* Staking reward;
* Airdrop;
* Gift;
* Other.

Для перевода между собственными кошельками система должна позволять связать исходящую и входящую транзакции в одну логическую операцию.

Такие переводы не должны изменять размер общего капитала кроме уплаченной комиссии.

### 7.2 Неклассифицированные операции

Новые автоматически обнаруженные операции могут получать статус:

`Unclassified`.

На Dashboard пользователь должен видеть количество операций, требующих классификации.

## 8. Ручные операции

Пользователь должен иметь возможность:

* создать операцию;
* изменить операцию;
* удалить операцию.

Ручные операции необходимы для учета активов, которые система не может получить автоматически.

Например:

* покупка неизвестной системе криптовалюты;
* операции на бирже;
* наличные;
* другие активы.

Для операции должны поддерживаться:

* дата и время;
* актив;
* количество;
* стоимость операции;
* валюта;
* комиссия;
* тип операции;
* комментарий.

## 9. Корректировка автоматических данных

Автоматически импортированные blockchain-транзакции пользователь не должен физически удалять из истории blockchain.

Вместо этого система должна разделять:

* исходные данные (`raw transaction`);
* пользовательскую интерпретацию операции.

Пользователь может изменить:

* классификацию;
* комментарий;
* связанные активы;
* стоимость покупки/продажи;
* связь с другой транзакцией.

При повторной синхронизации изменения пользователя не должны теряться.

## 10. История изменения капитала

Система должна позволять отличить:

изменение капитала из-за движения рынка

от

изменения капитала из-за внесения или вывода средств.

Например:

Portfolio value:

`$100,000 → $110,000`

должно быть понятно, произошло ли это из-за:

* роста рынка на $10,000;
* внесения $10,000;
* комбинации обоих факторов.

Это необходимо для корректного отображения инвестиционной доходности.

## 11. Себестоимость активов

Для купленных активов система должна хранить стоимость приобретения.

Это позволит рассчитывать:

* Average Buy Price;
* Cost Basis;
* Unrealized P&L;
* Realized P&L.

Например:

BTC

Amount: `1.2 BTC`

Average Buy Price: `$55,000`

Current Price: `$80,000`

Cost Basis: `$66,000`

Current Value: `$96,000`

Unrealized P&L: `+$30,000`

## 12. Синхронизация

Система должна выполнять фоновые процессы:

* получение рыночных котировок;
* обновление blockchain transactions;
* обновление wallet balances;
* расчет стоимости портфеля;
* сохранение исторических snapshots.

Ошибки одного внешнего сервиса не должны блокировать работу всего приложения.

Пользователь должен видеть:

* время последней успешной синхронизации;
* состояние синхронизации;
* ошибку источника при наличии проблемы.

## 13. Защита от дубликатов

Повторная синхронизация не должна создавать дубли операций.

Для blockchain-транзакций идентификатором должна служить комбинация данных сети и transaction hash с учетом особенностей конкретного blockchain.

Для ручных операций система должна использовать собственный immutable ID.

## 14. Аудит изменений

Для важных пользовательских изменений желательно сохранять историю.

Например:

* операция была создана;
* изменена классификация;
* изменена стоимость;
* операция удалена.

Для MVP полноценный UI истории не обязателен, но архитектура должна позволять восстановить источник изменений.

## 15. Импорт и экспорт

Система должна позволять экспортировать данные пользователя.

Минимум:

* CSV.

Желательно:

* JSON backup.

Экспорт должен включать:

* assets;
* wallets;
* transactions;
* classifications.

В дальнейшем должна быть возможность импорта операций через CSV.

## 16. Data ownership

Все пользовательские данные должны храниться в собственной базе данных приложения.

Работа приложения не должна полностью зависеть от внешнего поставщика данных.

При недоступности внешнего API пользователь должен продолжать иметь доступ:

* к истории;
* операциям;
* предыдущим котировкам;
* структуре капитала.

## 17. MVP Scope

В первую версию входят:

1. Single-user account.
2. Email/password authentication.
3. Password recovery through email.
4. Mandatory TOTP 2FA.
5. Dashboard.
6. Portfolio value.
7. Portfolio history chart.
8. Asset allocation.
9. USD/EUR/RUB valuation.
10. Hourly market prices.
11. Historical price storage.
12. Manual assets.
13. Manual transactions.
14. BTC wallet tracking.
15. Ethereum wallet tracking.
16. Solana wallet tracking.
17. Automatic blockchain transaction import.
18. Transaction classification.
19. Detection of transfers between own wallets.
20. Fees.
21. Cost basis.
22. Realized/unrealized P&L.
23. CSV export.
24. Background synchronization.
25. Synchronization/error status.

## 18. Out of Scope for MVP

Не входят в первую версию:

* публичная регистрация;
* multi-user;
* social login;
* exchange API integrations;
* bank integrations;
* trading;
* отправка cryptocurrency;
* хранение private keys;
* tax reporting;
* mobile applications;
* stocks/bonds broker integrations;
* automatic tax calculation;
* DeFi protocols;
* NFT valuation.

Я бы особенно добавил четыре вещи, которых изначально не было в твоём описании: cost basis/P&L, различие между рыночной доходностью и внесением денег, концепцию raw transaction + user classification, а также переводы между своими кошельками. Без них через несколько месяцев накопления истории цифры на Dashboard начнут становиться экономически неправильными.

Ещё я бы сразу заложил одну важную модель: не хранить просто «текущий баланс актива». Источником истины должны быть операции, а баланс и стоимость портфеля — вычисляться из них. Периодически можно сохранять `portfolio_snapshot` для быстрого построения графиков. Это сильно упростит дальнейшее развитие системы.

Следующим шагом надо сделать уже нормальный набор Product Requirements → Epics → User Stories → Acceptance Criteria, включая структуру сущностей (`Asset`, `Wallet`, `Transaction`, `Price`, `PortfolioSnapshot`) и сценарии для ATDD/E2E. Для разработки через OpenSpec это будет гораздо полезнее, чем просто BRD и поручить задачи агентам-исполнителям, затем ревью, тестирование и деплой.
