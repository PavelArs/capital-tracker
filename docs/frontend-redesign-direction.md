# Manual MVP frontend direction — design kickoff

Status: design proposal, 2026-10-02. Source review is from this `design/mvp-frontend-direction` worktree (base `4a52f9f4f74543b4f199b88b3cf7d3784db4ec22`) and the separate `capital-tracker-manual-allocation` worktree. Root reports the allocation feature integrated in reviewed PR #29; critical real CI is in progress and deployment has not occurred. This design worktree has not verified that runtime. The companion [interactive reference](design/manual-mvp-reference.html) uses synthetic values and is not an application preview or accounting evidence.

## Product boundary and design decision

The working entry remains **Ручные счета**. The MVP answers: which manual accounts exist; what their selected, priced positions are worth at an exact UTC moment; what happened on one account; where prices or history are missing; and how to record, import, correct or void evidence. The selected-account result is a *preview* of up to 10 owner-chosen manual accounts, never an automatic whole-portfolio balance. It uses current effective history and saved manual USD prices at the exact requested instant. It excludes cash and connected wallets, and does not reconcile overlapping holdings. A full total and allocation percentage are unknown when evidence is incomplete. The priced subtotal is a visible partial amount, not a total. These statements come from `frontend/src/api/manual-portfolio-valuation.api.ts`, `manual-portfolio-view.ts`, and `ManualPortfolioValuation.tsx` in the separate allocation worktree.

Use the existing route hierarchy for this release: **Ручные счета**, **Переводы между счетами**, **Вводы и выводы**, **Ручные цены**, **Прибыль за период**, **Настройки**. Keep **Прежние данные** subordinate and explicitly legacy. Network connections, AI, and an automatic consolidated dashboard have no active navigation or mock controls. `frontend/src/App.tsx` already routes to the manual directory and keeps legacy surfaces distinct; `Layout.tsx` already has a skip link, current-route links, a narrow-screen menu and a mounted outlet. This direction refines content and rhythm without replacing those working safeguards.

## A cohesive interface system

**Tone.** Treat this as a precise financial workbench. Borrow early desktop software's compact rows, quiet borders and visible controls. Use a warm neutral canvas (`#f5f4f0`), white panels (`#fff`), dark ink (`#24303a`), muted ink (`#52616a`), steel-blue action (`#315c78`), pale active background (`#eaf1f5`), hairline border (`#cbd3d6`). Status adds words and an icon/left rule; color alone conveys nothing. Dark theme uses existing theme variables and must pass a measured contrast review before implementation acceptance; color inversion is insufficient. No shadows for ordinary cards, gradients, animated navigation, floating glass or oversized metric tiles.

**Type and spacing.** Keep system UI fonts that render Cyrillic reliably; no added webfont. Base 16px/1.45 on all viewports (do not drop to 14px at 480px); H1 25–28px, H2 19–21px, labels 14–15px with 600 weight, table data 14–15px, supporting text at least 13px. Use tabular numerals; preserve exact strings and allow wrap/copy rather than rounding or ellipsis. Spacing steps 4, 8, 12, 16, 24, 32px. Panel padding 16–20px and row minimum 44px for action targets; compact evidence rows may be smaller when not touch controls. Max readable explanatory measure about 72 characters; results and tables use available width.

**Hierarchy.** Each page has one H1, a short scope line and one main action. Use section labels for tasks, not abstract analytics terminology. Result areas start with what was calculated and its date/scope, then the primary value or explicit unknown, then missing-data counts, then exact supporting rows. Technical revision pins, coverage, IDs and original versions stay one disclosure away and remain copyable. Scope warnings sit immediately before or after the result they qualify; a longer method explanation belongs in native `details` with an honest summary. Avoid repeated paragraphs at page top and every card.

**Controls and feedback.** Form labels remain visible above inputs. Put units in labels (**USD**, **%**, **UTC**), a concrete ISO example next to time fields and inclusive/exclusive boundary help where it matters. Group related fields, show required review affirmation by its submit action, and associate validation text with the field. Keep one primary action in a form and make secondary actions plain bordered buttons. Saving announces progress, blocks duplicate writes, retains draft; definite error gives a fix and retry; unknown delivery shows the frozen original-command retry and disables new writes until reconciled. Empty states say why and offer the real next action. Missing history, missing price, unavailable rate and zero are four different states. Error and success status must be announced and readable in light and dark themes.

**Tables.** Use true table markup for comparable financial rows, caption and labelled columns. Right-align exact numeric columns with `font-variant-numeric: tabular-nums`; keep time, amount, unit and status visible. At 360px, an explicit named `role="region"` scroll area with keyboard focus contains wide evidence tables; put a compact row summary above only when it is derived from the same record. Do not hide columns in a way that removes audit evidence. Give horizontal scroll a visible affordance and avoid page-level overflow.

**Navigation.** Desktop 1440: 240px left rail, persistent route state, 24px content gutters; useful content starts within the first viewport. Tablet 768: in-flow header with labelled **Меню**, then full-width task content; avoid a rail that crushes tables. Phone 360: menu closed by default; show page identity, scope and primary action before any long explanation. Keep menu keyboard escape, focus return and current-route semantics already present. For account workspace, stack back link → account title → 3 section buttons (wrap or full-width select if needed) → workflow select → active task. Hidden task panels remain mounted so draft, CSV File and recovery identity survive switching and resize; changing route/account follows existing ownership and stale-response rules. No overlay or transition is needed.

## Responsive reference and priority sequence

The [standalone reference](design/manual-mvp-reference.html) shows a synthetic selected-account directory/result and account workspace at 360, 768 and 1440px. It has a working menu, view switcher, account selection, sample complete/incomplete result switch and details disclosure solely to let a reviewer inspect hierarchy and states. It makes no API calls and cannot calculate a real valuation. At 1440, selection and result form a 2-column work area with tables below; at 768 and 360 they stack. The main number is **Не определена** in the incomplete sample, while **Оценённая часть** remains a separate partial amount.

1. **First bounded OpenSpec slice — `redesign-selected-manual-valuation`.** Start from the reviewed PR #29 integration commit once its contract is available in the implementation worktree; keep the in-progress critical CI and release gates separate. Make the directory's valuation entry visible, clarify loaded-catalogue selection, and reduce dense prose by moving method detail into an accessible disclosure. In the result, show status, exact total or unknown, priced subtotal, missing counts and the short scope warning before audit tables. Make both wide result tables named, keyboard-focusable scroll regions with visible focus and a short mobile scroll cue; allow long instrument names to wrap while keeping `th scope="row"`, exact quantity/value/share cells and copyable full identities. Use existing React/CSS and API; no new library, backend, migration, deployment or lockfile changes. Allowed implementation files: `frontend/src/pages/ManualAccounts.tsx`, `frontend/src/pages/AccountDirectory.css`, `frontend/src/features/manual-portfolio-valuation/ManualPortfolioValuation.tsx`, `frontend/src/features/manual-portfolio-valuation/ManualPortfolioValuation.css`, and focused existing frontend tests for those components. Optional shared token adjustment belongs in a separately reviewed shell slice. Preserve selector limit, pagination honesty, stale-response invalidation, exact strings, loaded accounts, null semantics, and 409 handling. Do not combine with release operations.
2. **Account read hierarchy.** Bring account name, chosen task, latest exact result and local warning into a stable first viewport. Adjust `ManualAccountDetail`, `AccountWorkspace`, `AccountOperations`, and their CSS in a separate change. Keep every hidden mounted editor and all correction/retry guards. Resolve narrow-screen section navigation and long identities there.
3. **Operation review rhythm.** Apply the same compact evidence/action pattern to trades, swaps, rewards and CSV, then transfers, flows and prices in bounded changes. Characterize each workflow before moving controls; do not unify financial commands under a new generic state machine.
4. **Period and settings finish.** Clarify profit/XIRR/TWR side by side only where space supports it, with separate unavailable states. Apply the same controls to Settings and login/MFA. Review legacy screens and chart maximum-period behavior separately; no misleading automatic portfolio home.
5. **Whole-screen visual acceptance.** Inspect real app states in light and dark at 360/768/1440, keyboard and reduced motion, then update the isolated local preview with synthetic data for owner review. Prior scoped visual checks are not whole-redesign approval.

### First-slice OpenSpec and evidence contract

Propose the first slice with stable scenarios before implementation: **VAL-UI-SELECT** (loaded catalogue, 0/1/10 selections, limit and later page), **VAL-UI-COMPLETE** (complete selected preview, exact account/instrument totals and percentages), **VAL-UI-INCOMPLETE** (missing journal/price or pre-coverage: unknown total and share, distinct priced subtotal, exact counts), **VAL-UI-STALE** (change account/instant during request; late response cannot replace new intent), **VAL-UI-ERROR** (409, network failure, retry and retained input), **VAL-UI-KEYBOARD** (menu, selector, calculation, disclosure, table region and focus), **VAL-UI-SCOPE** (cash/wallet/overlap limits adjacent to result). Reuse existing financial assertions; a rendering snapshot alone does not establish these behaviors.

Record expected interaction failure before changing source where behavior is added. Run relevant frontend unit tests, lint/build/type checks and strict OpenSpec validation. For acceptance, run selected real HTTPS/MFA/PostgreSQL journeys on an isolated synthetic runtime: complete and incomplete selected valuations, one missing-price case, exact 10-account/loaded-page selection, stale in-flight response, and account navigation back to the retained selection. Inspect actual browser frames at 360/768/1440, light/dark, with zoom/keyboard checks; record source/image identity, test IDs, passed/failed/unrun checks and screenshots. The design HTML has only static markup and interaction checks; it is not those runtime tests. Owner visual review remains a separate gate before calling the whole frontend done.

## Design-reference verification, 2026-10-02

The local installed Playwright Chromium rendered six **synthetic HTML** frames: `/private/tmp/manual-mvp-reference-{360,768,1440}-{light,dark}.png`. For each frame the browser reported `scrollWidth=clientWidth` (360/768/1440 respectively), two named focusable table scroll regions and H1 **Ручные счета**. No page errors occurred. Automated interaction checks selected a complete single-account example, then an incomplete example, verified the displayed total and instrument row count changed, entered the account-view example, and found no page-level overflow. I visually inspected the 360 light, 768 dark, 1440 light and 1440 dark frames; the compact header, stacked work area, result warning and contained tables are legible. This is visual/layout evidence for the local reference only. Contrast ratios, zoom, screen reader behavior and a live application were not measured. No production data, accounting API, PostgreSQL, HTTPS/MFA journey, release artifact or deployment was used.
